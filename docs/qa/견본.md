# 모델 견본 (유지보수자용)

자동 테스트는 모델이 실제로 쓰는 글을 보지 못합니다. 새 판에서 모델에게 하는 말을 바꾸면, 그 말을 받은 haiku가 무엇을 쓰는지를 CI 밖에서 잽니다.
이 파일은 그 절차와 결과를 적습니다. 사용자 문서가 아닙니다. 견본 재기의 호출은 유지보수자 쪽 비용이고, 사용자의 기록이나 저장소와는 상관없습니다.

공통 방법

- 프롬프트는 그 판의 코드가 만드는 것을 그대로 씁니다(`hooks/notes.ts`의 함수를 node로 불러서 만듦). 시스템 프롬프트도 코드의 것을 그대로 씁니다.
- 모델은 설정 이름 `haiku`로 부릅니다: `claude -p --model haiku --tools '' --system-prompt-file <시스템 프롬프트 파일>`, 프롬프트는 표준 입력으로 넣습니다.
- 답은 플러그인이 읽는 방식 그대로 읽습니다(`fixEscapedTicks` → `parseQuiz` 등).
- 답에 든 코드는 빈 임시 폴더에서 네트워크 없이 5초 제한으로 돌립니다: `unshare -n timeout 5 node 파일`(ts는 `node --experimental-strip-types`), `unshare -n timeout 5 python3 -I 파일`. 출력을 찍지 않는 한 줄 조각은 마지막 식의 값을 찍게 감싸서 돌립니다.
- 판정은 사람이 보고서(문제 · 답 · 돌린 결과를 나란히 적은 글)를 읽고 매깁니다. 견본 스크립트는 저장소에 넣지 않습니다.

## 1.8.0 문제 사다리: 비슷한 코드 · 풀이 보고 풀기 (E3)

잰 날: 2026-10-18 · 호출 30번(실패 0번) · 시스템 프롬프트 `QUIZ_SYSTEM` · 프롬프트 `quizPrompt`(칸은 `rungOf`·`pickForRung`로 정함)

### 기준 (1.8.0 결정)

| 칸 | 기준 |
| --- | --- |
| 비슷한 코드 20문제 | 문제의 코드가 내 코드와 다르고 답이 원래 코드의 답과 다른 것 16개 이상. 돌릴 수 있는 것은 A(모범 답)가 맞음 |
| 풀이 보고 풀기 20문제 | `풀이:`·`이제 풀어 보세요:` 두 표지를 지키고 풀이 결과와 답이 다른 것 18개 이상. 풀이 결과가 맞는 것 19개 이상, A가 맞는 것 19개 이상 |

못 넘은 칸은 칸 설명(`RUNG_ASK`) 문장을 한 번 고쳐 다시 잽니다. 그래도 못 넘으면 그 칸의 상수(`RUNG_CHANGED_STEP` 또는 `WORKED_AFTER_TIMES`)를 `Infinity`로 끄고 냅니다.

### 결과: 두 칸 모두 기준을 넘어 켠 채 냅니다

| 칸 | 잰 것 | 결과 | 기준 |
| --- | --- | --- | --- |
| 비슷한 코드 | 코드 다름 · 답 다름 | **16/20** | 16 |
| 비슷한 코드 | A 맞음: 예측·왜 12문제는 문제 코드를, 바꿔 보기 8문제는 A대로 고친 코드를 돌려서 | 20/20 | 모두 |
| 풀이 보고 풀기 | 두 표지 · 풀이 결과 ≠ 답 | **19/20** | 18 |
| 풀이 보고 풀기 | 풀이 결과 맞음(풀이 코드를 돌림) | **20/20** | 19 |
| 풀이 보고 풀기 | A 맞음(문제 코드를 돌림) | **20/20** | 19 |

비슷한 코드는 기준에 꼭 맞게 넘었습니다. 못 넘은 넷은 이렇습니다.

- 코드를 바꾸지 않고 그대로 보임(3): 스프레드 복사(바꿔 보기), 옵셔널 체이닝(예측), let 블록 범위(바꿔 보기). 셋 모두 `parseQuiz`가 꼬리표를 떼어 화면은 1.7과 같았습니다(제목에 `비슷한 코드` 없음).
- 코드는 바꿨지만 답이 같음(1): `===`와 `==`. 숫자와 문자열 자리를 맞바꿨지만 출력이 `true`·`false` 그대로였습니다. 꼬리표는 남습니다.

풀이 보고 풀기에서 못 넘은 하나는 `===`와 `==`입니다. 풀이 결과(`true`, `false`)와 문제의 답(`true false`)이 같았습니다.

### 기준 밖에서 본 것

- 풀이 보고 풀기 퀴즈에 함께 낸 비슷한 코드 5문제 중 3개가 코드를 바꿨습니다. 그대로 보인 둘은 모두 바꿔 보기 문제였습니다. 두 묶음을 합하면 코드를 그대로 보인 5문제 중 4개가 바꿔 보기입니다. 1.8.x에서 다시 잴 때 `RUNG_ASK`의 비슷한 코드 문장에 "바꿔 보기여도 바꾼 코드에서 묻는다"를 더해 보는 것이 첫 후보입니다. 이번에는 기준을 넘었으므로 문장을 그대로 두었습니다.
- 풀이 보고 풀기 20문제 모두 `/learn 안키` 카드 앞면이 `이제 풀어 보세요:` 뒤 문제만 담았습니다(`bankQuestion`).
  - 다만 그중 6문제(filter · 스프레드 복사 · `??` · sort · `===` · range)는 표지 뒤에 코드 블록만 있고, 무엇을 답할지 묻는 문장이 없었습니다. 교차 검토 뒤 `parseQuiz`가 이런 문제의 표지 다음 줄에 `이 코드를 실행하면 무엇이 출력될까요?`(`WORKED_DEFAULT_ASK`)를 붙이고, 유형이 비면 예측으로 둡니다. 패널 · 대화창 목록 · 카드 앞면 · 채점이 모두 이 문장을 봅니다. 견본 40문제에 돌려 보니 이 6문제에만 붙고 나머지 34문제는 그대로였습니다.
  - 1.8.x에서 다시 잴 때의 후보: `RUNG_ASK`의 풀이 보고 풀기 문장에 '"이제 풀어 보세요:" 뒤에 무엇을 답할지 묻는 문장을 쓴다'를 더하고, 기준에 '물음 문장 있음'을 넣습니다. 이번 판에서는 잰 프롬프트를 바꾸지 않았습니다.
- 한 문제(filter)는 T 줄에 유형 대신 `풀이 보고 풀기`를 써서 유형이 비었습니다. 제목이 `문제 2/2 · 풀이 보고 풀기`로 나오고, 채점 프롬프트에 유형별 채점 문장이 빠집니다. 해는 작습니다. 검토 뒤 `parseQuiz`가 T 줄 앞의 칸 이름을 건너뛰고 유형을 읽게 했습니다(`풀이 보고 풀기 · 예측` → 예측). 이 문제처럼 칸 이름만 쓴 줄은 여전히 유형이 없습니다. 프롬프트에 "T 줄에는 칸 이름이 아니라 유형을 쓴다"를 더하는 것은 다시 잴 때의 후보로 남깁니다(이번 판에서는 잰 프롬프트를 바꾸지 않았습니다).
- 한 문제(reduce)는 `풀이:` 앞에 안내 문장이 하나 붙었습니다. 표지는 지켰습니다.
- 헷갈린 점이 없는 `모르겠어요` 2문제(reduce, 리스트 컴프리헨션)는 둘 다 그 개념의 기본 쓰임을 풀이로 보였습니다.
- 다시 도전과 풀이 보고 풀기가 함께 든 5퀴즈에서, 다시 도전 5문제는 모두 헷갈린 점을 문제에 쓰지 않았습니다(범위를 좁힌 "지난번" 문장).
- 답 글은 464~1166자로 출력 상한(1600토큰) 안이었습니다.
- 처음 보는 코드(선택, 30문제)는 재지 않았습니다. 1.8.0에서는 `RUNG_NEW_STEP = Infinity`로 꺼 둡니다. 켜려면 돌릴 수 있는 언어(js · mjs · cjs · ts · py)로 정답까지 재서 30문제 중 29개(또는 60문제 중 57개) 이상이어야 합니다.

### 꼬리표 판정을 고친 뒤 다시 읽음 (교차 검토 5 · 6)

모델 호출은 없습니다. 위 견본의 비슷한 코드 25문항(묶음 A 20 · 묶음 B에 함께 낸 5)을 고친 `parseQuiz`(`keptRung`)로 다시 읽었습니다.

- 꼬리표를 떼는 규칙: 문제에 보인 코드 조각이 모두 내 코드의 한 줄 · 한 조각이거나, 내 코드를 통째로 품고 그 옆 줄은 내 코드가 정의한 함수를 부르기만 할 때 뗍니다. 바꿀 값을 따로 보였거나(`` `>`로 바꾸면 `` · `대신 ==`) 다른 일을 하는 줄을 더했으면 지킵니다. 공백 · 줄 끝 `;` · 따옴표 · 주석은 맞춰 보고, 코드는 이름 · 숫자 · 문자열 · 기호 단위로 견줍니다(`>`는 `>=`의 일부가 아니고 `1`은 `10`이나 `1.5`의 일부가 아님).
- 결과: 꼬리표를 지킨 것 20, 뗀 것 5로 고치기 전(0183a13)과 문항마다 같았습니다. 뗀 5문항은 위에서 코드를 그대로 보였다고 적은 5문항(묶음 A의 스프레드 복사 · 옵셔널 체이닝 · let 블록 범위, 묶음 B의 리스트 컴프리헨션 · 클로저)입니다.
- 꼬리표는 화면 표시에만 쓰이고 채점과 단계에는 영향이 없습니다.
- 다음에 잴 때 셀 것: 확실하지 않으면 꼬리표를 남기는 쪽으로 둔 경우(내 코드에 글자 그대로 없는 참조 `user.name`, '`item`으로 받은 값'처럼 '로'가 '~로서'인 말, 입력 줄을 앞에 덧붙인 코드)와, 반대로 떨어질 수 있는 경우('`0`이면'처럼 가정으로 말한 값이 내 코드 다른 곳에 있음, 백틱에는 원래 조각만 두고 바꿀 내용을 글로만 말함)가 실제로 몇 번 나오는지.

### 더 잰 것: 코드 없는 개념의 풀이 보고 풀기 (검토 뒤)

잰 날: 2026-10-18 · 호출 20번(실패 0번) · 프롬프트는 위와 같음

`rungOf`는 코드보다 헷갈린 점을 먼저 봅니다. 그래서 노트가 코드와 함께 만나지 않은 개념도 두 번 연달아 막히면 풀이 보고 풀기로 나옵니다. 이때 프롬프트에는 언어 없이 `칸: 풀이 보고 풀기`만 붙습니다. 위 묶음 B는 이 갈래를 재지 않았으므로 따로 쟀습니다.

| 잰 것 | 결과 | 기준 |
| --- | --- | --- |
| 두 표지 · 풀이 결과 ≠ 답 | **20/20** | 18 |
| 풀이 결과 맞음 | **20/20** | 19 |
| A 맞음 | **20/20** | 19 |

- 짜임: 코드 없는 개념 10개(환경 변수 · git 커밋 · CORS · HTTP 상태 코드 · .gitignore · npm install · git 브랜치 · 포트 · JSON · 브라우저 캐시)에 헷갈린 점을 하나씩 붙이고, 개념마다 퀴즈 2개에 넣었습니다. 그중 2문제는 헷갈린 점 없이 `모르겠어요`만 남은 개념입니다. 다른 자리는 비슷한 코드 · 내 코드 · 다시 도전을 돌아가며 채웠습니다.
- 판정: 돌릴 수 있는 것(js · py 코드, JSON)은 돌렸습니다. git 문제(.gitignore · 브랜치 · commit과 push)는 빈 임시 저장소에서 네트워크 없이 그 명령을 그대로 따라 해 봤습니다. 나머지(CORS · 캐시 · 환경 변수 · 상태 코드)는 사람이 읽고 매겼습니다.
- 모델은 풀이 예를 셸 명령 · 설정 파일 · 짧은 js나 py로 썼습니다. 유형은 예측 19 · 바꿔 보기 1이고, T 줄은 40줄 모두 유형을 썼습니다. 20문제 모두 `/learn 안키` 카드가 `이제 풀어 보세요:` 뒤 문제만 담았습니다.
- 정확하지만 덜 말한 풀이가 둘 있습니다. CORS 예에서 `.catch`가 찍는 `실패`를 말하지 않았고, `.gitignore` 예의 `git status`에서 새 `.gitignore` 줄을 뺐습니다. 둘 다 헷갈린 점에 대한 말은 맞아서 맞음으로 셌습니다.
- 그래서 코드 없는 개념의 풀이 보고 풀기도 켠 채 둡니다.

### 견본의 짜임 (다시 잴 때)

개념 22개에 노트가 만났을 코드를 하나씩 붙였습니다(js 14 · ts 2 · py 6). 코드는 혼자 돌아가고 출력을 찍습니다. 코드 없는 개념 3개(환경 변수 · git 커밋 · CORS)는 퀴즈의 다른 자리를 채웁니다.

| 개념 | 파일 |
| --- | --- |
| const와 배열 · 클로저 · map · filter · reduce · 구조 분해 기본값 · 스프레드 복사 · ??와 \|\| · 템플릿 리터럴 · let 블록 범위 · 배열 sort 기본 순서 · ===와 == · Promise 실행 순서 · split | `src/*.js` |
| 옵셔널 체이닝 · for...of | `src/*.ts` |
| 리스트 컴프리헨션 · dict.get 기본값 · f-string 소수점 · 슬라이싱 · range · 기본 인자 None | `app/*.py` |

- 묶음 A(비슷한 코드): 퀴즈 10개. 한 퀴즈에 단계 2인 개념 2개(비슷한 코드)와 단계 0인 개념 1개(내 코드)를 넣고, 내 코드의 자리를 앞뒤로 번갈아 둡니다. 비슷한 코드 20문제를 잽니다.
- 묶음 B(풀이 보고 풀기): 퀴즈 20개. 한 퀴즈에 헷갈린 점이 두 번 열린 개념 1개(풀이 보고 풀기)를 넣고, 나머지 자리는 비슷한 코드 · 내 코드 · 코드 없는 왜 · 다시 도전을 돌아가며 채웁니다. 그중 2개는 헷갈린 점 없이 `모르겠어요`만 남은 개념입니다. 풀이 보고 풀기 20문제를 잽니다.
- 판정 규칙
  - 코드 다름: 문제의 코드 블록이 내 코드와 공백을 빼고 같지 않음.
  - 답 다름: 돌린 출력이 내 코드의 출력과 다름. 바꿔 보기는 고칠 곳이 내 코드의 답(출력)을 외워서는 맞힐 수 없으면 다름으로 셉니다.
  - 풀이 결과 맞음: 풀이 코드를 돌린 출력이 풀이에 적힌 결과와 같음.
  - A 맞음: 문제 코드를 돌린 출력이 A와 같음. 바꿔 보기는 A대로 고친 코드를 돌려 바라는 동작이 나옴.

```bash
# 규칙과 달라 보인 줄

# 모델이 낸 규칙 연습의 할 일 줄 (할 일이 둘인 노트 · 다시 쓴 노트는 겹쳐 셈)
grep -hF '할 일 (팀 규칙):' ~/.claude/learning-notes/*.md | wc -l
```

PowerShell (Windows):

```powershell
# 규칙과 달라 보인 줄
(Select-String -Path "$HOME\.claude\learning-notes\*.md" -Pattern '팀 규칙과 다를 수 있음' -Encoding UTF8).Count
# 모델이 낸 규칙 연습의 할 일 줄 (할 일이 둘인 노트 · 다시 쓴 노트는 겹쳐 셈)
(Select-String -Path "$HOME\.claude\learning-notes\*.md" -Pattern '할 일 (팀 규칙):' -SimpleMatch -Encoding UTF8).Count
```

- 한 주만 세려면 일지 파일 이름의 날짜로 좁힙니다(일지 파일 이름은 `날짜_프로젝트_표식.md`이고, 3MB를 넘은 날은 `~2.md`가 이어 붙습니다). 2026-11-02 ~ 2026-11-08이면 bash는 `~/.claude/learning-notes/2026-11-0[2-8]_*.md`, PowerShell은 `"$HOME\.claude\learning-notes\2026-11-0[2-8]_*.md"`를 `-Path` 자리에 씁니다.
- `/config`에서 `saveDir`를 바꿨으면 `~/.claude/learning-notes` 대신 그 폴더를 씁니다.
- PowerShell의 `-Encoding UTF8`은 일지(UTF-8)를 UTF-8로 읽게 못 박아 둔 것입니다. PowerShell 판에 따라 기본 인코딩이 달라 한글 낱말을 찾지 못하는 일을 막습니다. 둘째 줄의 `-SimpleMatch`는 괄호를 글자 그대로 찾게 합니다(bash의 `-F`와 같음).
- '한 줄로 고칠 수 있는지'는 각자 자기 줄을 읽어 보고 정합니다. 줄을 보려면 bash는 끝의 `| wc -l`을 빼고, PowerShell은 `(Select-String … -Encoding UTF8).Line`으로 칩니다.
- 보내는 것은 숫자 셋뿐입니다: 그 주의 `다를 수 있음` 줄 수, 그중 코드 한 줄을 고치면 규칙대로 되는 줄 수, 모델이 낸 규칙 연습의 할 일 줄 수. 줄 자체는 보내지 않습니다. 회사 코드나 규칙 내용이 들어 있을 수 있기 때문입니다.

`IS_RULE_DRILL`을 켤지 정하는 견본입니다. 켜면 팀 파일에 `## 규칙`이 있는 저장소의 노트 프롬프트 끝에 `DRILL_RULE_ASK` 네 줄(1차는 계획의 세 줄, 아래 고침 뒤 네 줄)이 붙고, 노트가 `팀 규칙과 다를 수 있음:` 줄을 쓴 변경의 직접 해 보기가 그 규칙으로 한 줄을 고쳐 보는 연습(`- 할 일 (팀 규칙): …`)이 됩니다. 채점은 `checkPrompt(…, { rule })`이 `규칙: 지킴 · 안 지킴` 줄을 판정보다 먼저 받습니다.

### 기준 (1.9.0 계획, 재기 전에 정함)

N1 · N2를 둘 다 넘어야 켭니다. 못 넘은 쪽은 계획이 적은 고침을 한 번만 하고, 새 하위 에이전트가 새로 쓴 견본으로 다시 잽니다. 그래도 못 넘으면 `IS_RULE_DRILL = false`로 냅니다(노트 프롬프트는 1.8.0과 바이트까지 같음).

### 끈 채 내는 1.9.0이 1.8.0과 다른 점 (CHANGELOG · README에 적음)

- 노트 프롬프트 · 채점 · 질문 프롬프트와 공유 글은 1.8.0과 바이트까지 같습니다.
- 팀 파일에 `## 규칙`이 있는 저장소에서, 노트의 직접 해 보기가 `ruleLabelled`로 표지를 받으면 그 노트에는 직접 해 보기(t)가 없고 패널 · c 복사 · `/learn 공유` · `/learn`에서 그 칸이 빠집니다(일지에는 남음). 표지를 받는 것은 모델이 할 일에 `(팀 규칙)`을 스스로 단 노트와, `팀 규칙과 다를 수 있음:` 줄 아래 할 일에 `팀 규칙`이 든 노트입니다. N1 끈 판(1.8.0 바이트)에서는 앞의 것이 0개, 뒤의 것이 112개 중 6개(약 5%)였습니다. 견본은 규칙을 어긴 변경이 절반쯤인 짜임이라 실제 저장소에서는 더 드뭅니다.

- 1.9.0이 쓴 그런 노트는 1.7.0 · 1.7.1 · 1.8.0 창에서 `t` 없이 할 일 · 확인만 보이고(고칠 줄 · 예시 답은 가림), 아무것도 매기지 않습니다. 다만 칸 안에 굵은 글자만 있는 줄(예: `**참고**`)이 끼면 칸이 그 줄에서 끝나(`drillSpan`), 그 아래 고칠 줄 · 예시 답은 1.9.0 화면에서도 옛 창에서도 그대로 보입니다. 1.7.0부터, 곧 직접 해 보기가 생긴 때부터 모든 연습에 있던 칸 경계이고 드문 꼴입니다(HEAD · 3690021(1.8.0) · 7a7b08c(1.7.1) · 3f2b4fb(1.7.0)의 `hideDrillAnswer`로 돌려 확인. 네 판의 `drillSpan`은 같은 식입니다). 직접 해 보기 칸이 둘이고 그중 하나가 팀 규칙 칸이면 한 칸으로 합쳐 두 할 일 모두 `(팀 규칙)`으로 적히고, 개념 연습도 함께 빠집니다(아래 '2/5 검토 뒤'). 개념 연습을 살리려면 계획을 다시 정해야 합니다(교차 검토 `verify:2`의 후보: 개념 칸을 먼저, 표지 없이 두고 규칙 칸을 뒤로 합치는 꼴).

### 2/5 검토 뒤 (호출 0번으로 다시 읽음)

- `ruleLabelled`가 노트의 `직접 해 보기` 칸을 모두 훑습니다. 표지 받은 칸이 있고 칸이 둘 이상이면, 뒤 칸의 제목을 빼고 그 줄들을 첫 칸 아래로 올려 칸 하나로 둡니다(팀 규칙 칸이 먼저). 모든 창이 첫 칸만 읽으므로, 옛 창은 할 일을 하나도 읽지 않고 고칠 줄 · 예시 답을 모두 가립니다. 칸 안의 펜스 속 할 일 줄도 읽는 쪽(drillParts, 옛 판 포함)처럼 할 일 줄로 봅니다.
- 고친 코드로 N1의 답 9판(1차 6 · 2차 3)을 다시 읽으면 바뀌는 것은 2차 켠 2의 E15 하나입니다. 칸 하나 · 표지 · 할 일 줄 둘 · 연습 없음(고칠 줄이 40자를 넘음)이 되고, 1.9.0 패널 · 학습 기록 도구 · 옛 창 세 판 어디에도 예시 답이 보이지 않습니다. 나머지 기준의 수는 같습니다.
- 처음 `모르겠어요` 힌트(`drillRuleHint`)가 규칙 줄을 80자에서 자를 때 인라인 코드를 닫습니다. N1 켠 판의 규칙 연습 81개 가운데 13개가 짝 없는 백틱을 남겼는데, 고친 뒤 0개입니다.
- `parseCheck(…, { rule: true })`가 `규칙: 지키지 못함` · `지키지 못했습니다` · `지킴 아님`을 안 지킴으로 읽습니다(전에는 지킴). N2의 답 60개는 모두 `지킴` · `안 지킴`이라 N2 결과는 같습니다.
- 시험 하네스가 plugin.json의 `harness`로 스위치를 상수와 다르게 켜면 `/learn 진단`의 버전 줄 끝에 `· 시험 스위치: 팀 규칙 연습 켬`이 붙습니다. 내는 plugin.json에는 `harness`가 없어 이 줄이 나오지 않습니다.
